# Feature Specification: 修復 GoatCounter 自訂點擊事件

**Feature Branch**: `speckit-trial`

**Created**: 2026-11-19

**Status**: Draft

**Input**: User description: "修復舞吉站 GoatCounter 自訂點擊事件（Kanzo 卡 team#16）。現況：taisui2027/index.html 三個購買 CTA 已加 data-goatcounter-click（event/cta-payhip-taisui-result、event/cta-payhip-tiangan、event/cta-payhip-taisui-tg），各頁都載入 //gc.zgo.at/count.js（站台 wujitycoon.goatcounter.com），另有 trackTiangan() 用 goatcounter.count({event:true}) 送 event/tiangan-lookup；但上線兩天後 GoatCounter /api/v0/paths 仍完全沒有任何 event/* 路徑。需求：1) 找出事件沒被記錄的原因並修好，讓 CTA 點擊（含 target=_blank 外連到 Payhip/Portaly 的連結）與天干查詢都會可靠送出 GoatCounter 事件；2) 全站凡是指向 payhip.com 或 portaly.cc 的外連都要能記錄點擊事件，事件名稱規則一致；3) 要有可重複執行的自動化測試（無頭瀏覽器攔截送往 goatcounter 的請求，不真的送出以免污染數據），在手機 390px 與桌機 1280px 都驗證事件會送出、版面不壞；4) 不加其他追蹤器、不新增外部依賴。不要建立新 git 分支，留在目前分支 speckit-trial。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 購買 CTA 點擊被可靠記錄 (Priority: P1)

身為站長，我需要知道訪客是否真的點擊了購買 CTA，才能判斷行動卡商品的轉換成效。現況是三個 CTA 已標記但事件完全沒有出現在追蹤報表，等於沒有任何可依據的數據。本故事要求找出事件未送出的原因並排除，讓每一次真實點擊都留下事件紀錄，即使連結會另開分頁到外部商店也一樣。

**Why this priority**: 這是變現成效的唯一依據；沒有事件資料就無法評估商品頁與文案，問題已持續兩天，影響最直接。

**Independent Test**: 在獨立的驗證環境開啟 2027 犯太歲查詢頁，分別點擊三個購買 CTA，攔截送往 GoatCounter 的請求，確認每次點擊都產生對應的事件名稱與事件標記；此測試不依賴天干查詢或全站其他頁面即可完成。

**Acceptance Scenarios**:

1. **Given** 訪客已完成出生年查詢並看到查詢結果卡，**When** 點擊「買完整白話行動卡 PDF」CTA（另開新分頁前往 payhip.com），**Then** 系統送出一個事件，名稱為 `event/cta-payhip-taisui-result`，且原頁面仍可繼續操作。
2. **Given** 訪客停留在日主速查卡，**When** 點擊「買 2027 十天干財運行動卡」CTA，**Then** 系統送出一個事件，名稱為 `event/cta-payhip-tiangan`。
3. **Given** 訪客停留在日主速查卡，**When** 點擊「犯太歲行動卡」CTA，**Then** 系統送出一個事件，名稱為 `event/cta-payhip-taisui-tg`。
4. **Given** 追蹤程式碼比頁面內容晚準備好，訪客在追蹤程式碼準備好之前就點擊 CTA，**When** 追蹤程式碼完成準備，**Then** 該點擊事件仍被補送，不會永久遺失。
5. **Given** 任一 CTA 的追蹤請求被封鎖或失敗，**When** 連結導航發生，**Then** 訪客仍可正常抵達外部商店，頁面不顯示錯誤訊息。
6. **Given** 訪客在短時間內連續點擊同一 CTA 三次，**When** 追蹤請求被攔截，**Then** 攔截到恰好三筆事件，沒有額外重複。

### User Story 2 - 天干查詢事件可靠記錄 (Priority: P2)

身為站長，我想知道有多少人實際使用日主（天干）查詢功能，以判斷這項免費工具是否值得繼續維護。目前查詢動作有事件名稱但同樣沒有出現在報表，需要一併修好。

**Why this priority**: 僅次於 conversion；這是頁面核心功能的使用指標，可獨立於購買 CTA 驗證。

**Independent Test**: 在驗證環境直接填寫有效國曆生日並按下查詢按鈕，攔截追蹤請求，確認產生 `event/tiangan-lookup`；不需要點擊任何購買 CTA 即可完成。

**Acceptance Scenarios**:

1. **Given** 訪客在日主速查卡輸入有效生日，**When** 按下查詢按鈕並成功算出日主，**Then** 系統送出一個 `event/tiangan-lookup` 事件。
2. **Given** 訪客透過附帶有效日期參數的分享網址進入頁面，**When** 頁面載入並成功算出日主，**Then** 系統送出一個 `event/tiangan-lookup` 事件。
3. **Given** 訪客只勾選「晚上 11 點」選項或輸入無效日期，**When** 沒有新的有效查詢結果產生，**Then** 不送出 `event/tiangan-lookup` 事件。
4. **Given** 一次成功的查詢動作，**When** 事件送出後，**Then** 只產生一筆事件，不因重複渲染而加倍。

### User Story 3 - 全站商店外連一致追蹤 (Priority: P3)

身為站長，我希望全站每一個通往 Payhip 或 Portaly 的連結都能被追蹤，而且事件名稱有一致規則，這樣日後新增商品或更換商店時，報表仍然可讀、可比較。目前只有犯太歲頁的三個連結有標記，其他頁面若出現同類外連就會形成資料黑洞。

**Why this priority**: 確保資料完整與長期可維護性；在 Core 事件修好後，避免日後新增外連再次遺漏。

**Independent Test**: 掃描所有頁面，找出每一個指向 payhip.com 或 portaly.cc 的外連並逐一點擊或模擬點擊，確認每一個都送出具規則的事件名稱；不需要依賴特定頁面的查詢結果。

**Acceptance Scenarios**:

1. **Given** 全站任一頁面存在指向 payhip.com 或 portaly.cc 的外連，**When** 訪客點擊該連結，**Then** 系統送出一筆事件，且事件名稱符合一致的命名規則。
2. **Given** 同一頁面在不同區塊各有一個通往相同商店的連結，**When** 分別點擊兩者，**Then** 產生兩筆事件，名稱能區分其所屬頁面或區塊，互不覆蓋。
3. **Given** 日後新增指向 payhip.com 或 portaly.cc 的外連，但未另行逐頁標記，**When** 訪客點擊該連結，**Then** 仍自動被納入追蹤並依規則命名。
4. **Given** 連結指向非 Payhip 且非 Portaly 的網站（例如資料來源），**When** 訪客點擊，**Then** 不因此產生本規則的事件。
5. **Given** 既有三個 CTA 事件名稱與 `event/tiangan-lookup`，**When** 規則套用後，**Then** 名稱保持不變，歷史資料不被拆成新舊兩組。

### User Story 4 - 可重複執行的雙視埠自動化驗證 (Priority: P4)

身為站長，我需要一個可重複執行的驗證方式，在不污染正式資料的前提下，確認事件真的會送出且版面沒有壞掉。目前只能靠人工檢查，無法在每次修改後快速確認。

**Why this priority**: 這是交付品質關卡；有了它才能確保前三個故事日後不會悄悄退化，並滿足雙視埠自檢要求。

**Independent Test**: 執行同一個自動化程序兩次以上，比較結果是否一致，並確認正式追蹤服務的資料沒有增加。

**Acceptance Scenarios**:

1. **Given** 驗證環境以無頭瀏覽器載入頁面，**When** 測試點擊任一 CTA 或觸發查詢，**Then** 送往追蹤服務的請求被攔截並記錄，而非真正送到正式站台。
2. **Given** 測試以 390px 視埠執行，**When** 完成所有事件案例，**Then** 事件全部送達攔截端，且頁面沒有水平溢出、CTA 可見可點、文字沒有被裁切或重疊。
3. **Given** 測試以 1280px 視埠執行，**When** 完成所有事件案例，**Then** 事件全部送達攔截端，且版面配置正常、CTA 可見可點。
4. **Given** 連續執行測試多次，**When** 比較每次結果，**Then** 通過與失敗項目一致，沒有偶發性失敗。
5. **Given** 測試執行完畢，**When** 查詢正式追蹤報表，**Then** 測試期間沒有新增任何事件筆數。
6. **Given** 修改已完成，**When** 盤點全站頁面與測試程序，**Then** 僅保留原有追蹤服務，且沒有新增任何外部依賴。

---

### Edge Cases

- 追蹤程式碼尚未載入、載入失敗，或被內容封鎖器擋下時，購買導航與天干查詢功能仍完全可用，且使用者看不到錯誤。
- 以新分頁（`target="_blank"`）開啟外部商店時，事件仍能送達，不因原分頁切換或新分頁立即關閉而遺失。
- 短時間內快速連續點擊同一 CTA，或重複載入相同的分享網址，每次使用者操作只產生一筆事件。
- 同一個外部商店連結在同一頁面的不同區塊重複出現時，各自事件的名稱能區分來源區塊。
- 無效日期、空白輸入或僅更改選項時不產生天干查詢事件。
- 測試或本機環境的請求不得寫入正式追蹤資料，即使測試中途失敗也要維持攔截。
- 在 390px 與 1280px 兩種視埠下，CTA 與查詢結果區塊都不得出現水平捲動、元素重疊或文字裁切。
- 非商店類外連（資料來源、首頁導覽等）不被本規則的事件名稱涵蓋。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統必須找出並排除導致自訂事件未出現在追蹤報表的原因，使事件能被實際記錄。
- **FR-002**: 系統必須在訪客點擊任一通往 Payhip 或 Portaly 的購買連結時，送出一筆 GoatCounter 事件。
- **FR-003**: 系統必須在追蹤程式碼尚未準備好時暫存點擊與查詢事件，並於準備完成後補送，不得永久遺失。
- **FR-004**: 系統必須確保每一次有效的點擊或查詢只產生一筆事件，不重複送出。
- **FR-005**: 系統必須在連結以新分頁開啟外部商店的情況下，仍於導航前後可靠送出事件。
- **FR-006**: 系統必須維持現有三個 CTA 事件名稱（`event/cta-payhip-taisui-result`、`event/cta-payhip-tiangan`、`event/cta-payhip-taisui-tg`）不變。
- **FR-007**: 系統必須在天干查詢成功（含按鈕查詢與有效分享網址載入）時送出 `event/tiangan-lookup`，且無效查詢不送出。
- **FR-008**: 全站每一個指向 `payhip.com` 或 `portaly.cc` 的外連都必須被追蹤，包含日後新增的連結，不依賴逐頁手動標記。
- **FR-009**: 商店外連事件名稱必須遵循一致規則：以 `event/cta-` 開頭，接平台識別（`payhip` 或 `portaly`），再接頁面或區塊與用途，全部使用小寫與連字號，`event/` 後不得為空。
- **FR-010**: 追蹤失敗或被封鎖時，系統必須維持頁面功能與外部導航正常，且不得向使用者顯示錯誤。
- **FR-011**: 必須附帶一個可重複執行的自動化測試程序，使用無頭瀏覽器攔截送往 GoatCounter 的請求並驗證事件內容，請求不得真正送出。
- **FR-012**: 自動化測試必須同時在 390px 與 1280px 視埠驗證事件送出與版面完整性（無水平溢出、無元素重疊、CTA 可見可點）。
- **FR-013**: 自動化測試連續執行多次的結果必須一致，且執行後正式追蹤服務的事件筆數不增加。
- **FR-014**: 本功能不得加入 GoatCounter 以外的任何追蹤服務，也不得新增外部依賴套件。

### Key Entities *(include if feature involves data)*

- **追蹤事件**: 一筆記錄使用者意圖的資料，具事件名稱、來源頁面或區塊、送出時間與事件標記；事件名稱以 `event/` 開頭並遵循一致命名規則。
- **商店外連**: 任何目標為 `payhip.com` 或 `portaly.cc` 的連結，具所屬頁面、所屬區塊、目標商品與對應事件名稱。
- **攔截請求**: 自動化測試在請求抵達追蹤服務前取得的紀錄，包含事件名稱與事件標記，用於驗證且不寫入正式資料。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 三個既有購買 CTA 在驗證環境的點擊事件送出率達 100%，且事件名稱與現有名稱完全一致。
- **SC-002**: 全站所有指向 Payhip 或 Portaly 的外連，點擊後產生對應事件的比率達 100%，事件名稱符合規則的比例達 100%。
- **SC-003**: 每一次有效點擊或有效查詢產生的事件筆數恰好為 1，重複送出率為 0%。
- **SC-004**: 天干查詢（含分享網址載入）的事件送出率達 100%，無效查詢的事件數為 0。
- **SC-005**: 在 390px 與 1280px 兩種視埠下，所有事件驗證案例通過率達 100%，且版面檢查沒有任何水平溢出或元素重疊。
- **SC-006**: 自動化測試連續執行 3 次，結果完全一致，且正式追蹤站台新增事件數為 0。
- **SC-007**: 追蹤功能失效或被封鎖時，購買導航與天干查詢仍可完成，成功率達 100%。
- **SC-008**: 修改後的全站頁面中，追蹤服務數量維持為 1（僅 GoatCounter），外部依賴新增數為 0。

## Assumptions

- 現有 GoatCounter 站台與程式碼載入方式維持不變，本次僅處理事件未送出的原因與外連涵蓋範圍。
- 事件名稱沿用既有的 `event/` 前綴與小寫連字號格式；既有三個 CTA 名稱與 `event/tiangan-lookup` 保持不變，以維持歷史資料連續性。
- 本站為靜態頁面、無伺服器端程式，所有追蹤行為在使用者瀏覽器端完成；驗證環境已有可用的瀏覽器與執行工具，故不新增外部依賴。
- 自動化測試以本機提供的頁面進行，並在請求送往追蹤服務前加以攔截；測試流量不計入正式資料。
- 僅記錄使用者主動點擊商店外連與有效天干查詢，不記錄自動化流量、滑過或無效輸入。
- 非 Payhip 與 Portaly 的外連（例如資料來源與站內導覽）不在本次追蹤規則範圍內。
